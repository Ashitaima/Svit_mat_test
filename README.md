## 1. Події, які потрібно збирати

Кожна подія містить **спільні поля**:

- `event_id` (UUID): унікальний id події, генерує клієнт; потрібен для захисту від дублів
- `event_type`: тип події
- `occurred_at`: коли подія сталася (час клієнта); `received_at` ставить сервер
- `session_id` (UUID): є навіть в анонімного користувача
- `user_id`: заповнений, якщо користувач залогінений, інакше NULL
- `page_url` і `properties` (JSON з полями конкретного типу)

Пропоную **7 типів подій** (`*` означає обов'язкове поле):

- **`product_view`**: перегляд картки товару
  - `product_id`\*, `price`, `currency`, `category_id`, `source` (search / catalog / recommendation)
- **`add_to_cart`**: додавання товару в кошик
  - `product_id`\*, `quantity`\* (> 0), `price`\*, `currency`\*
- **`remove_from_cart`**: видалення товару з кошика
  - `product_id`\*, `quantity`\*
- **`checkout_started`**: початок оформлення замовлення
  - `cart_value`\*, `currency`\*, `items_count`\*
- **`order_created`**: замовлення створено (надсилає сервер)
  - `order_id`\*, `total`\*, `currency`\*, `items[]` (product_id, quantity, price)
- **`payment_succeeded`**: успішна оплата (надсилає сервер)
  - `order_id`\*, `amount`\*, `currency`\*, `payment_method`
- **`payment_failed`**: невдала оплата (надсилає сервер)
  - `order_id`\*, `amount`, `reason` (declined / timeout / …)

Події замовлення й оплати надсилає **бекенд**, а не браузер: клієнтську подію можна загубити
(закрита вкладка, adblock) або підробити, а факт оплати знає лише сервер після відповіді
платіжного провайдера. `user_agent`, IP та UTM-мітки зберігаються один раз на сесію, а не
в кожній події.

## 2. API для прийому подій

**Ендпоінт:** `POST /api/v1/events`.

- Приймає **пакет** від 1 до 100 подій: `{ "events": [ ... ] }`. Клієнт накопичує події й
  відправляє раз на кілька секунд або при закритті сторінки (`navigator.sendBeacon`).
  Так менше запитів і менше втрачених подій.

  Приклад тіла запиту:

  ```json
  { "events": [ {
      "event_id": "0193a1b2-7c4d-7e8f-9a0b-1c2d3e4f5a6b",
      "event_type": "add_to_cart",
      "occurred_at": "2026-11-17T09:10:00Z",
      "session_id": "33333333-3333-3333-3333-333333333333",
      "user_id": 2,
      "page_url": "https://shop.example/p/502",
      "properties": { "product_id": 502, "quantity": 1,
                      "price": 499.00, "currency": "UAH" }
  } ] }
  ```

- Відповідь **`202 Accepted`**:
  `{ "accepted": 4, "duplicates": 1, "rejected": [ { "index": 2, "errors": [...] } ] }`.
- Помилки: `400` (не JSON / немає `events`), `413` (більше 100 подій або тіло > 512 KB),
  `429` (rate limit).

Псевдокод обробника у файлі [**`ingest_handler.py`**](ingest_handler.py)

**Валідація** відбувається у два рівні:

1. **Увесь запит:** тіло є JSON, `events` є непорожнім масивом до 100 елементів, розмір до
   512 KB. Інакше `400` / `413`.
2. **Кожна подія окремо** (JSON Schema для кожного `event_type`):
   - є обов'язкові поля `event_id`, `event_type`, `occurred_at`, `session_id`; UUID валідні,
     `event_type` зі списку відомих
   - `occurred_at` не пізніше `now + 5 хв` (розсинхрон годинника) і не раніше `now − 7 днів`
   - є обов'язкові поля свого типу; `quantity > 0`, `price ≥ 0`, `currency` має 3 літери ISO-4217
   - серверні типи (`order_created`, `payment_*`) приймаються лише з серверним API-ключем

Невалідна подія не валить увесь пакет: вона потрапляє в `rejected` з індексом і причиною,
решта подій зберігається.

## 3. Структура бази даних

**Таблиці та зв'язки** (PostgreSQL):

- **`users`**: `id`, `email`, `created_at`
- **`sessions`**: `id` (UUID), `user_id` → users (NULL для аноніма), `started_at`,
  `last_seen_at`, `user_agent`, `utm_*`
- **`orders`**: `id`, `user_id` → users, `session_id` → sessions, `status`, `total_amount`,
  `currency`, `created_at`, `paid_at`; позиції лежать в **`order_items`** (`order_id`,
  `product_id`, `quantity`, `unit_price`)
- **`events`**: `event_id` + `occurred_at` (PK), `event_type`, `session_id`, `user_id`,
  `product_id`, `order_id`, `page_url`, `properties` (JSONB), `received_at`;
  партиціонована по місяцях
- **`daily_product_stats`**: попередньо пораховані метрики по днях для дашбордів

Зв'язки: users 1 → N sessions, sessions 1 → N events, sessions 1 → N orders,
orders 1 → N order_items. Гроші рахуємо з `orders`, а події потрібні для поведінки й воронок.
На `events` свідомо немає foreign keys: це найнавантаженіша на запис таблиця, і перевірка FK
на кожен INSERT дорога.

SQL-схема у файлі [**`sql/schema.sql`**](sql/schema.sql)

**Найбільша таблиця:** **`events`**. Решта таблиць ростуть разом із кількістю людей і покупок,
а `events` росте з кожною дією: одна сесія дає десятки подій, а конверсія в e-commerce
становить 1–3%, тож на одне замовлення припадають сотні подій. При 50 тис. сесій на день
це ~1 млн рядків на день.

**Що робити, якщо вона швидко росте:**

- **Партиціонування по часу** (вже в схемі, по місяцях): запит за місяць читає лише одну
  партицію, старі дані видаляються миттєвим `DROP PARTITION` замість повільного `DELETE`.
- **Retention:** сирі події 3–6 місяців тримаємо в БД, потім вивантажуємо в дешеве сховище
  (S3 / Parquet).
- **Агрегати:** дашборди читають маленьку `daily_product_stats`, а не мільйони сирих рядків.
- **Мінімум індексів**, бо кожен індекс сповільнює вставку.
- Далі: черга (Kafka / RabbitMQ) перед БД для згладжування піків і колонкова БД (ClickHouse)
  для аналітики.

## 4. Базова аналітика та одна проблемна ситуація

1. **Перегляди товару за день:** групування `product_view` по дню й товару; рахуються всі
   перегляди (`COUNT(*)`) і унікальні сесії (`COUNT(DISTINCT session_id)`), бо одна людина
   може оновити сторінку кілька разів.
2. **Конверсія «кошик → оплата»:** сесії з `add_to_cart` за період (знаменник), з них ті,
   де **після** першого додавання в кошик була `payment_succeeded` (чисельник).
   На демо-даних: 3 сесії з кошиком, 2 з оплатою, **66.67%**.
3. **Воронка по днях:** перегляд → кошик → checkout → оплата одним проходом через
   `COUNT(DISTINCT ...) FILTER (WHERE ...)`.
4. **Бонус:** ідемпотентне наповнення агрегату `daily_product_stats`
   (`INSERT … ON CONFLICT DO UPDATE`).

Запити у файлі [**`sql/queries.sql`**](sql/queries.sql), демо-дані для перевірки
у [**`sql/seed.sql`**](sql/seed.sql)

**Проблема.** Клієнт відправив пакет, сервер його записав, але відповідь загубилася (обрив
мережі, таймаут). Клієнт надсилає той самий пакет ще раз, і без захисту події запишуться
двічі, а метрики завищаться.

**Рішення: ідемпотентність через** **`event_id`**.

1. Клієнт генерує `event_id` (UUID) **один раз у момент події** і при повторі надсилає
   той самий id.
2. У БД стоїть унікальний ключ `(event_id, occurred_at)`, вставка йде через
   `INSERT … ON CONFLICT DO NOTHING`: дубль ігнорується без помилки.
3. Сервер відповідає на дубль успіхом (`202`, лічильник `duplicates`), і клієнт видаляє
   подію зі своєї черги.

Для оплат бекенд робить `event_id` детермінованим (UUIDv5 від `order_id`), а `occurred_at`
бере з `orders.paid_at`, тож повторний webhook дає ту саму пару ключів і не створить
другу оплату в аналітиці. Перевірку дубля
видно в [`sql/seed.sql`](sql/seed.sql): одна подія вставляється двічі, а в таблиці
лишається один рядок.
